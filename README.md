# 推测解码验证台（Speculative Decoding Verifier）

用 FastAPI + CPU 版 PyTorch 实现的网页应用，验证**推测解码能否在保证输出完全一致的
前提下节省目标模型的前向调用**，并验证**被拒绝的草稿不会污染后续生成**。

所有模型权重在进程内以固定随机种子生成，**无需下载任何模型**；词表为固定的 98 个
字符级 token，草稿与目标模型共用。

## 目录结构

```
app/
  tokenizer.py   固定字符级词表（pad/unk/eos + 95 个可打印 ASCII，共 98 token）
  model.py       带 KV 缓存的小型因果 Transformer + 固定权重的草稿/目标模型
  decoding.py    无缓存逐 token 贪心基线 与 带 KV 缓存的推测解码
  main.py        FastAPI 路由、对照序列化、固定预设
static/
  index.html     单页前端（对照输出、逐轮接受数、前向次数、首处分歧标记）
tests/
  test_decoding.py  11 项关键功能测试
Dockerfile / docker-compose.yml  容器化启动
```

## 模型设计（均为固定权重、确定性可复现）

| 模型 | 层数 | 注意力头 | d_model | 说明 |
|---|---|---|---|---|
| 目标模型 | 4 | 4 | 128 | 被核验的大模型 |
| 草稿模型 | 1 | 2 | 128 | 提议草稿的小模型 |

- 二者**共享 token 嵌入与 LM head（权重绑定）**，词表共用；
- 草稿主体在同一初始化 RNG 流之后，再用独立固定种子（seed=99）注入受控高斯扰动
  （σ=0.125）。该尺度经实测使两模型首 token 预测翻转率约 30%，从而同一服务内
  既能稳定观测到**整块接受**，也能稳定观测到**拒绝**；
- 完全独立初始化会导致未训练模型 argmax 近乎 100% 不同（几乎全拒绝），完全一致
  又不会拒绝，受控扰动是让两条路径都可演示的关键。

## 推测解码算法要点

1. 用户设置每轮草稿数 `k ∈ [1,4]`、最多新 token 数 `max_new ∈ [1,32]`；
2. 每轮草稿模型基于**自身 KV 缓存**逐 token 增量写出最多 `k` 个草稿；
3. **目标模型每轮只做 1 次前向**，整块核验草稿；首轮输入「提示词+草稿块」，
   之后每轮输入「上一轮 pending 的纠正/补词 token + 新草稿块」，
   **已缓存前缀绝不重算**；
4. 逐位比对目标贪心预测与草稿 token：
   - 拒绝：丢弃被拒位置及之后的草稿，采用目标在该位置的纠正 token，并把目标/草稿
     KV 缓存截断回滚到接受前缀（回滚无污染，有专项测试）；
   - 整块接受：额外采用目标基于整块上下文的补词 token；
5. `max_new` 上限与 EOS 截断在两条路径上语义完全一致（EOS 计入输出，其后停止）；
6. argmax 平局取词表序号小者（`torch.argmax` 返回首个最大值，天然满足）。

**缓存不变量**：每轮开始时目标缓存覆盖确认前缀倒数第二个 token，pending 保存上一轮
tail；草稿缓存对齐完整确认前缀。因此目标前向次数恒等于推测轮数。

## 正确性保证

推测解码输出在拒绝、整块接受、EOS、达到上限等所有情况下，都与「目标模型**无缓存、
逐 token、对完整前缀重算**的贪心基线」**逐 token 完全相同**。前端在不一致时会标出
首个分歧位置（token id 与文本）并判定 FAIL。

## 启动方式

### Docker Compose（推荐）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

镜像基于 `python:3.11-slim`，通过 PyTorch 官方 CPU index 安装
`torch==2.5.1+cpu`，不含 CUDA 依赖；带 `/api/health` 健康检查。

### 本地直接运行

```bash
pip install --index-url https://download.pytorch.org/whl/cpu torch
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## 接口

- `GET /api/health`：服务与模型信息；
- `GET /api/presets`：返回固定的「拒绝」「整块接受」两条预设提示词；
- `POST /api/decode`：入参 `{prompt, k(1~4), max_new(1~32)}`，返回两种方式的
  token 序列、解码文本、目标/草稿前向次数、逐轮核验明细、节省统计与一致性判定。

## 实测结果（CPU，torch 2.15.0+cpu，单线程）

测试命令：`python tests/test_decoding.py`，**11 项全部通过**。

- 84 组参数组合（7 提示词 × 4 个 k × 3 个 max_new）下，推测解码与贪心基线
  逐 token 完全一致；
- 缓存/无缓存两条前向路径的 argmax 决策逐位相同（logits 仅 ~1e-5 级 float32
  舍入差异）；缓存回滚后续写与整序列前向逐位一致；
- 前向次数（k=4、max_new=32）：
  - 整块接受预设：基线 **32** 次目标前向 → 推测 **7** 次（减少约 78%）；
  - 拒绝预设（首轮接受后持续被拒）：基线 32 次 → 推测 **28** 次，且输出仍与
    基线完全一致，证明被拒草稿未污染后续生成；
- 强制注入 EOS 后，4 个 k × 3 个上限组合下两条路径 EOS 位置与截断完全一致；
- FastAPI TestClient 与真实 `uvicorn` 启动均验证通过，参数越界返回 422、
  空提示词返回 400。

> 说明：拒绝预设的前向节省为负向示例——当草稿质量差时推测解码不会节省调用，
> 这正是本验证台要展示的权衡；输出正确性不受影响。
